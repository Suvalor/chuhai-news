# chuhainews 文章推送规则与注意事项

本规则记录 2026-11-16 从邮件推荐清单推送文章的做法。字段及接口行为以当前 [WebHook Schema](../app/webhook_schema.json)、[README](../README.md#webhook-协议) 和服务端代码为准。推送前确认用户要求的内容形式和发布范围。

## 选文和内容准备

1. 读取用户指定的邮件、附件或链接清单。表格中的类目和入选理由是线索，逐条打开原帖，核对作者、正文、发布时间、链接和可见的互动数据。
2. 无法读取或核实的条目记录原因并报告。作者的收入、粉丝或增长数字写明是作者自述，除非有其他可靠证据独立核实。
3. 根据本次用户要求决定是全文、译文还是编者整理。2026-11-16 这批经用户确认采用中文要点，正文开头明确注明「编者整理」并提供原帖链接。课程预告只按预告介绍，不补写原帖没有的策略。
4. 准备标题、正文和必要的编者导读。summary 是编辑部判断，用于正文前导读和页面描述。原文与译文分段对齐，译文在推送前准备好。
5. 检查站点已有内容和稳定的 external_id。相同 external_id 会更新已有文章。摘要与已有文章是否合并，先核对用户意图和目标记录。

## 推送前检查

| 字段 | 填写和核对 |
| --- | --- |
| external_id、source_url | 至少提供一个，建议同时提供。同一 ID 会更新整篇。本批中文要点使用 editorial-summary:x:<帖子ID>。 |
| author、title、lang | 作者 handle 和名称与原帖一致。标题符合实际内容，语言字段对应正文。编者整理在标题或正文标明。 |
| category | 使用站点已有 key，例如 cog、money、ai、tool、global、create。 |
| paragraphs 或 body | 正文必填。支持段落、小标题和 HTTPS 图片。正文与导读准确标明来源和内容形式。 |
| published_at | 优先使用原帖明确显示的发布时间，写成含时区的 ISO 8601。缺省会使用入库时间，影响排序。帖子 ID 时间可作线索，编辑过的帖子或时间含义不明确时再核对。 |
| views、likes、saves | 分别填写来源浏览、点赞和收藏数，记录采集时间。只显示「3.6万」等约数时注明精度。无法核实的字段留空并报告。 |
| status | 按用户本次指令选择 published 或 draft。未指定时结合上下文判断，存在实质歧义时核实。 |

当前 Schema 没有回复数和转帖数字段。站点展示的浏览、点赞、收藏数是来源数加本站增量。更新时提供的这三个来源数会替换先前来源数，本站增量保留，未提供的这三个数保持原值。

## WebHook 投递

1. 读取线上 GET /api/webhook 的当前 Schema。WEBHOOK_SECRET 保存在项目本地 .env 或其他已授权的安全配置，不写入代码、文档、日志、聊天或 Git。
2. 向 POST /api/webhook 发送 JSON。推荐 HMAC-SHA256 签名，消息字节为「时间戳 + 点号 + 原始请求体」，请求头使用 X-Chuhai-Timestamp 和 X-Chuhai-Signature。时间戳与服务器偏差需在五分钟内。也支持 Bearer 认证，具体格式见 README。
3. 每批最多 100 篇、5 MB。单篇校验失败会使整批校验失败，422 的 index 指向出错条目。遇到超时或异常，先核对已入库记录再决定重试。同一 ID 重试可能更新正文。签名请求每次重试使用新的时间戳并重新签名。
4. 2026-11-16 的 Python-urllib/3.13 请求被 Cloudflare 浏览器完整性检查以 HTTP 403、1010 拦截。使用表明用途的 User-Agent chuhainews-webhook/1.0 后，签名请求返回 HTTP 200。这是当时的排查结果，后续以实际安全事件和配置为准。出现拦截先查看 Cloudflare 安全事件，401 检查认证，429 按限流提示等待。
5. 对照回执核对 ok、external_id、created 和网址。created 为 false 表示更新既有记录，逐项确认是否符合预期。

## 更新已有文章

当前 WebHook 按 external_id 更新整篇文章，不是仅更新请求中提供的字段。回填前取得并保全现有完整记录，核对标题、正文、译文、作者、类目、来源、摘要、封面、状态、发布时间、阅读分钟数和自定义 slug。需要时通过后台或授权数据源确认。公开只读文章 API 不包含所有字段，不能仅凭它重建完整更新请求。提交后复核这些字段和计数，避免覆盖用户后续编辑。

## 交付核验

- 分别报告成功、更新、失败、跳过的条目及网址。成功以 WebHook 回执和站点状态为依据，草稿在后台核验。
- 对照原帖核对标题、作者、类目、日期、来源链接、正文形式和互动快照，尤其检查用户指定的数据。
- 标明约数、未核实数字和作者自述，以及采集时间。当前未建立来源指标实时刷新的承诺。
- 本次代码在整批校验后逐条写入。中断后按实际结果逐项核对，不能把提交尝试等同于全部完成。

## 本次经验

首次推送遗漏了来源浏览、点赞、收藏数以及大多数原帖发布时间，随后回填了 10 篇。初次回填使用公开只读 API 重建请求，而该接口缺少封面等字段。今后更新先取得完整记录，避免覆盖已有内容。已写入的互动数据是当时快照，原帖数值可能继续变化。
