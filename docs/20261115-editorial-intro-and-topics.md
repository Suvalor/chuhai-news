# 结论

站点的技术底座已经齐了：JSON-LD、sitemap、robots、llms.txt、逐篇 `.md` 都有。目前缺的是**原创增量**。整站内容都是翻译别人的 X 长文，搜索引擎和 LLM 看到原帖与本站时，都会优先原帖。本方案分三步补上：

1. **导读**：每篇文章开头放 2～3 句编者判断。复用现有 `summary` 字段，不加列。
2. **关于页**：说明谁在选、按什么标准选、怎么翻译。
3. **专题页**：人工策划的主题合集。等真实文章够多再做。

外部蓝图里的价格页、竞品对比、故障排查、带参深链、页脚「Ask ChatGPT」按钮都针对单产品工具站，不适用于本站，不做。FAQPage Schema 对普通站已拿不到富结果，也不做。

另外有一件比这三步都重要、但不属于代码的事：**部署上线，提交 Google Search Console 和 Bing Webmaster**。没被收录之前，以上优化都看不出效果。

# 现状（2026-11-15 读代码确认）

- `articles.summary` 已存在。WebHook 字段 `summary` ≤600 字，后台编辑页也能填。目前只用作 `meta description`、JSON-LD `description`、RSS、`/api/articles` 和 MCP 的摘要。**页面正文、`.md`、`llms.txt` 都没有它。**
- `data/real.db` 只有 2 篇真实文章，`summary` 都为空。
- 没有关于页，`Organization` 只出现在 Article 的 `publisher` 里。
- 已有类目页 `/c/<key>`（6 个类目）和作者页 `/u/<handle>`，按热度自动排序，没有人工编排。

# 一、导读（先做）

**定义**：说清作者的核心判断，以及它对做出海的人意味着什么，2～3 句、约 80～200 字。不写「本文介绍了……」。要的是编者自己的判断。

**做法**：继续用 `summary` 字段，在下面四处露出：

| 位置 | 改动 | 文件 |
|---|---|---|
| 阅读页 | 标题和作者信息下方、正文之前显示「导读」块；没有 summary 就不显示。滚动续读加载的下一篇也走这个模板，会一起带上导读 | `app/templates/_article.html` |
| `.md` | 元数据列表后、「原文」之前加 `## 导读` | `app/main.py` `to_markdown` |
| `llms.txt` | 每行链接后的说明优先用 summary 的第一句，没有就保持现状（译名标题） | `app/main.py` `llms` |
| WebHook 说明 | `summary` 的 description 改成「导读：编者对本文的判断，2～3 句；同时作 SEO 描述」 | `app/webhook_schema.json`、README |

`meta description` 的约 160 字截断交给搜索引擎处理，不另设字段。

**不做**：自动生成导读。导读要有价值，靠的就是人或上游 Agent 的判断，本站不调用 LLM。

**验收**：
- pytest：有 summary 的文章，阅读页 HTML、`.md` 和 `llms.txt` 都包含它；没有 summary 的文章不出现空的导读块。
- 浏览器：1440 宽和 390 宽下各看一次阅读页，导读块不挤压标题、旋转字环和翻译开关。
- 给 `real.db` 的 2 篇补上导读，作为真实样例。

# 二、关于页

**路由**：`/about`，服务端渲染一个模板。`base.html` 目前没有页脚，入口放顶栏还是新增页脚，到实现时再定。`llms.txt` 开头加一行指向它，`sitemap.xml` 收录。页面挂 `AboutPage` 加 `Organization` 的 JSON-LD。

**内容**（事实部分需要布佳糖美式提供，Agent 不代填）：
- 谁在运营、为什么做这个站
- 选文标准：什么样的长文会被收录
- 翻译方式：人工、AI 辅助还是人工校对，要如实写
- 版权处理：原帖链接、作者署名、联系删除的方式
- 更新频率

**验收**：pytest 检查 `/about` 返回 200、包含 JSON-LD，且 `llms.txt` 和 sitemap 里有它的链接。

# 三、专题页（门槛：真实文章 ≥30 篇后再做）

**为什么要设门槛**：一个专题至少需要 5～8 篇好文章撑场。现在只有 2 篇，做出来就是空壳页，反而降低整站质量。

**设计草案**（到时再定）：
- 新表 `topics(key, title, intro, items JSON[{slug, note}], status, updated_at)`。`note` 是这篇入选的一句理由。
- 路由 `/t/<key>`，复用现有 `CollectionPage` 的 JSON-LD 和列表模板；后台加增改；同步进 sitemap、`llms.txt` 和 MCP。
- 首页或类目页加专题入口。

选题从出海读者的真实问题出发，例如「AI 产品冷启动获客」「定价与付费墙」「英文个人品牌」，不按类目机械切分。

# 风险

- **版权**：导读和关于页能提高被引用的概率，但全文翻译他人 X 长文的授权问题依然存在。关于页要给出联系删除的方式，并如实写清楚。
- **改动面**：第一、二步约涉及 6 个文件（`_article.html`、新增 `about.html`、`base.html`、`main.py`、schema、测试）加 README，按全局规则需要先确认再动手。

# 实施结果（2026-11-15）

三步已全部实施，用户已授权。pytest 25 项全过（新增 3 项：导读、关于页、专题，含 XSS 转义与空专题）。浏览器在临时库副本上检查了 1440 宽和 375 宽：阅读页导读、首页专题区、专题页、关于页、后台专题编辑页都正常，没有横向溢出。

- **待决定 1** 已按推荐处理：导读沿用 `summary` 一个字段。
- **待决定 2** 关于页内容由用户确认：运营署名「chuhainews 编辑部」；翻译方式「AI 翻译，未逐篇校对」；选文标准是一手经验、对出海或 AI 实操有用、X 上高互动。删除联系方式用新增的环境变量 `CONTACT_EMAIL`，**目前没有设置**，所以关于页暂时不显示联系方式。
- **待决定 3** 一次做完了。
- 专题的代码已就绪，但「真实文章 ≥30 篇再发布专题」这条门槛不变。前台只展示已发布、且至少有一篇在架文章的专题；文章全部下架的专题页会加 `noindex`。
- 两项偏离方案：`base.html` 没有页脚，关于页入口加在首页的页脚链接里；阅读页本来就没有页脚，所以不加入口。
- 没做：`real.db` 里 2 篇真实文章的导读没有填。导读是以编辑部名义写的判断，应由编辑部本人来写。
- 关于页中文文案不到 500 字，`lieflat-less-ai-tone` 的脚本拒绝检测，改为按规则人工核对，只把一处结论冒号改成了句号。
